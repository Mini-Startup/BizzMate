CAROUSEL / NAVIGATION BEHAVIOR
The section is an interactive service carousel presented through an asymmetrical grid.

Define the service sequence in a stable, explicit order. Navigation should work consistently from any control.

Previous:
- Move to the previous service in the sequence.
- From the first service, wrap to the final service if the carousel uses looping behavior.

Next:
- Move to the next service in the sequence.
- From the final service, wrap to the first service if looping behavior is enabled.

Selecting a card:
- Set that service as active.
- Update the featured card.
- Update the description area.
- Update active card state.
- Update the existing progress component.
- Restart the autoplay interval if autoplay is enabled.

Selecting the already active service:
- Do not restart an unnecessary visual transition or produce a redundant state change.
- If the product’s existing interaction pattern treats a click on the active card as a timer reset, this is acceptable, but avoid visual flicker.

Navigation arrows:
- Use the project’s existing icon/button conventions.
- Provide meaningful accessible labels such as “Previous service” and “Next service.”
- Make arrow controls real buttons, not decorative icons.
- Stop propagation when a nested arrow button exists inside a clickable card so that it does not accidentally trigger two different selection actions.
- Prevent accidental duplicate navigation from event bubbling.
- Make the controls keyboard accessible.

AUTOPLAY BEHAVIOR
The service carousel should automatically advance after a short interval, but it must remain comfortable to read and must not interfere with manual control.

Recommended initial behavior:
- Start autoplay only when the section is in or near the viewport.
- Use an interval of approximately 5–7 seconds between automatic changes. Treat this as a tuning target, not an absolute requirement.
- Advance to the next service in the sequence.
- The next service should become the featured card, and the description and progress indicator should update together.
- Do not advance during the middle of an active transition.
- After a manual card selection or previous/next navigation, reset the autoplay timer so the visitor gets a full viewing interval for the newly selected service.
- If the visitor leaves the section, pause autoplay.
- When the visitor returns, resume according to the implementation’s normal timer policy without immediately switching the service.
- Pause autoplay while the visitor is hovering over the carousel on devices that support hover.
- Pause while focus is inside the interactive carousel, or at minimum ensure keyboard users can interact without the content changing unexpectedly.
- Pause when the browser tab is hidden using the Page Visibility API, if the existing implementation can do this without unnecessary complexity.
- Disable autoplay when prefers-reduced-motion is enabled, unless the existing product requirements explicitly say otherwise.
- If the visitor interacts manually, do not override their action immediately with a timer tick.
- If the user explicitly pauses the carousel through the existing progress/navigation component, respect that paused state.
- Clean up all timers and event listeners when the component unmounts.

IMPORTANT AUTOPLAY DETAIL
Do not use setInterval in a way that causes overlapping transitions or stale active-index values. Prefer a carefully managed timeout that is reset after each selection, or another timer pattern that uses current state safely. The timer must never advance multiple cards at once because of a stale closure or repeated effect.

TRANSITIONS BETWEEN SERVICES
The user specifically wants the change between services to feel smooth, fast, and connected—not like an entirely new page or section is being loaded.

Use a restrained transition system with these principles:
- Keep the overall grid/container anchored in place.
- Do not animate the whole section’s width or height.
- The featured card should transition to the new service without a full-page fade or large sweeping movement.
- The selected card’s content can fade out briefly and the incoming content can fade in with a small directional translation.
- Use opacity and transform for animated content wherever possible.
- Target approximately 220–360ms for card/content transitions. Tune this against the existing design and actual browser performance.
- The incoming service should feel like the next item in a coherent sequence, not an unrelated card being swapped abruptly.
- For next navigation, a very small horizontal movement toward the left may imply forward progression; for previous navigation, reverse the direction. Keep the offset restrained, approximately 8–16px.
- Do not make the entire featured card travel across the page from one position to another. The card container stays in place; its content and selected-state presentation change within that stable geometry.
- Small cards should update their content and active state without unnecessary motion across the entire grid.
- The description area should crossfade or use a brief opacity/transform transition when its content changes.
- Avoid large blur effects, spring/bounce motion, elastic movement, rotation, zooming, or exaggerated 3D transforms.
- Do not use layout animation for every grid item when a normal content transition will work.
- Avoid flashing a blank frame between outgoing and incoming service content.
- If image/icon content changes, reserve its space to prevent layout shift.
- Avoid transitions that make text unreadable while the visitor is trying to read it.
- Do not animate every nested icon, label, and paragraph independently. Animate each card or content group as a unit.
- If an animation library is already installed and suitable, use it for a clean enter/exit transition. Otherwise implement the effect with CSS classes and a small state/transition mechanism.

SUGGESTED TRANSITION SEQUENCE
When the active service changes:
1. Keep the outer grid and card containers fixed in their final positions.
2. Trigger a short outgoing content transition on the featured card and description area.
3. Update the active service state from the shared service data.
4. Render the new title, icon, and description in the same stable content slots.
5. Apply the corresponding incoming direction based on whether the user moved forward or backward.
6. Update active card styling and progress state immediately or in sync with the new content.
7. Finish the transition within the intended short duration.
8. Restart the autoplay timer only after handling the manual or automatic navigation cleanly.

This is a conceptual sequence. Choose the simplest implementation compatible with the existing framework and avoid unnecessary intermediate React renders.

ACCESSIBILITY
- Use semantic section and heading elements.
- Use actual buttons for previous/next controls.
- Give controls accessible names.
- Keep the active service understandable to screen readers, using suitable state attributes such as aria-current or aria-pressed where appropriate.
- Ensure selecting cards works with keyboard input if the cards are interactive.
- If cards are implemented as buttons, do not nest buttons inside buttons. Use a non-interactive card container with separate sibling controls, or another valid semantic structure.
- If a card navigates to a destination page, use an anchor for that navigation and a separate button for carousel selection if both actions are needed.
- Do not rely on color alone to indicate the selected card.
- Respect prefers-reduced-motion by disabling or minimizing service-change transitions and disabling autoplay.
- Pause automatic changes while keyboard focus is inside the component so users can finish interacting.
- Do not move keyboard focus automatically when the active service changes.
- Keep all service content accessible when animations are disabled.
- Do not announce every autoplay change aggressively to screen readers. If an aria-live region is used for manually selected service updates, make its behavior deliberate and avoid noisy announcements during autoplay.

PERFORMANCE REQUIREMENTS
- Use CSS Grid/Flexbox for layout.
- Use a single shared active-service state.
- Do not recalculate the entire layout on every scroll frame.
- Do not introduce an animation library solely for this component if CSS transitions are sufficient.
- Avoid expensive filters, blur animations, large shadows, canvas, WebGL, or background video.
- Animate opacity and transform wherever possible.
- Keep the number of simultaneously animated elements small.
- Use stable keys when rendering the service list.
- Prevent layout shifts when titles, descriptions, or icons change.
- Avoid unnecessary React state updates.
- Clean up timeouts, observers, and listeners on unmount.
- Avoid autoplay timers while the page is hidden or the section is out of view.
- Ensure the section remains usable when autoplay is disabled or JavaScript animation is unavailable.

EDGE CASES TO HANDLE
- The service list has no items: render a safe empty state or omit the section according to existing project conventions.
- The list has one item: hide or disable previous/next navigation and autoplay.
- The active item is removed or the service data changes: ensure the selected index/ID remains valid.
- The visitor clicks previous or next rapidly: prevent overlapping animations and ensure the final active item is correct.
- The visitor manually selects a card while autoplay is about to advance: manual selection should win and the timer should reset.
- The visitor changes service during a transition: handle the new selection without a flicker or stale content.
- The section leaves the viewport: pause autoplay.
- The tab becomes hidden: pause autoplay.
- Reduced motion is enabled: remove or minimize transitions and disable autoplay.
- The progress component is used: keep its active state and the service selection synchronized.
- The visitor navigates past the first or last service: follow one consistent wraparound policy.
